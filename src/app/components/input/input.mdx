## When to use

**Use a text input** when the answer can't be listed ahead of time:

- Names, emails, addresses, amounts and codes.
- Searching or filtering a list.
- Longer comments or messages (a text area).

### Compared with look-alikes

| Component | People | Use it for |
|---|---|---|
| **Input** | Type anything | Open answers |
| [Select](?path=/docs/components-forms-select--docs) | Pick one of 8 or more | Long, known lists, like countries |
| [Radio group](?path=/docs/components-forms-radio-group--docs) | Pick one of 2–5 | Short lists that need a description |
| [Chip](?path=/docs/components-chip--docs) | Pick one or several of 2–7 | Short answers, often suggested |

If people would type one of a few known answers, offer the answers instead: it's faster, and nothing can be misspelled.

| 2 | **Field** | Always. Holds the value, or a placeholder when empty. |
| 3 | **Status icon** | The field is invalid, has a warning or is valid. |

| 5 | **Help text** | Optional. A hint people need before they type. |
| 6 | **Count** | `maxLength` with `showCount`. |

## Variants

Two variants, picked by how long the answer is.

<DeviceVariation title="Single line" of={InputStories.VarSingle}>

For answers of a few words. Enter submits the form.

- The default, so no `type` is needed.
- Set `type` to `email`, `tel`, `url`, `number`, `search` or `password` so browsers and phones help (see Behavior).

</DeviceVariation>

<DeviceVariation title="Text area" of={InputStories.VarTextarea}>

For answers of a sentence or more. Enter adds a new line.

- Add `type="textarea"`. `rows` sets the height (3 by default).
- Make it as tall as the answer you expect, so people don't think it's short.

</DeviceVariation>

<DeviceVariation
  title="Appearance"
  of={InputStories.Switchable}
  switches={[{ arg: 'appearance', label: 'Appearance', initial: 'outline', options: [
    { value: 'outline', label: 'Outline', short: 'O' },
    { value: 'filled', label: 'Filled', short: 'F' },
    { value: 'pill', label: 'Pill', short: 'P' },
  ] }]}
>

Use the switch in the toolbar; only `appearance` changes in the code. Keep one appearance per form.

- **Outline** (default): forms.
- **Filled:** search and toolbars, where a border would add clutter.
- **Pill:** single, casual fields, like a chat box or "Add a note".

</DeviceVariation>

## Size

<DeviceVariation title="Small, medium, large" of={InputStories.Switchable} sizeSwitch>

Use the switch in the toolbar. Only `size` changes in the code.

- **Small** (`sm`, 32px): dense web screens like tables, filters and toolbars.
- **Medium** (`md`, 40px, default): most forms.
- **Large** (`lg`, 48px): short forms where typing is the main task, like sign-in.

On phones fields are **48px** tall (**44px** small) with **16px** text. Switch the toolbar to Mobile to see it.

</DeviceVariation>

## Modifiers

One input each, so they work with either variant and any size.

<DeviceVariation title="Help text" of={InputStories.ModHelp}>

Add `helpText` for what people need to know **before** they type, like a format or why you're asking. Keep it to one line.

</DeviceVariation>

<DeviceVariation title="Optional" of={InputStories.ModOptional}>

Add `[optional]="true"` to show "(optional)". In most forms most fields are required, so marking the few optional ones is clearer than asterisks on everything.

</DeviceVariation>

<DeviceVariation title="Required" of={InputStories.ModRequired}>

Add `[required]="true"` for a red `*` and the native `required`. Use it when most fields in a form are optional, and explain the `*` once at the top.

</DeviceVariation>

<DeviceVariation title="Search" of={InputStories.ModSearch}>

`icon="search"`, `appearance="filled"` and `type="search"`. A search field's purpose is clear from its icon, so hide the label on screen with `[hideLabel]="true"`. It's still read by screen readers.

</DeviceVariation>

<DeviceVariation title="Clear button" of={InputStories.ModClear}>

Add `[clearable]="true"` for a × once there's text. It empties the field, keeps the focus there and emits `cleared`. Use it on search and filter fields.

</DeviceVariation>

<DeviceVariation title="Password" of={InputStories.ModPassword}>

`type="password"` always comes with a show/hide button, so people can check what they typed. Set `autocomplete` to `current-password` or `new-password` so password managers can help.

</DeviceVariation>

<DeviceVariation title="Prefix and suffix" of={InputStories.ModAffix}>

`prefix` and `suffix` add fixed text like `$` or `kg`, so people only type the number. Single line only.

</DeviceVariation>

<DeviceVariation title="Character count" of={InputStories.ModCount}>

`maxLength` with `[showCount]="true"` shows a count like "6 / 30". Show it when there's a limit people might reach.

</DeviceVariation>

<DeviceVariation title="Auto-resize" of={InputStories.ModAutoResize}>

On a text area, `[autoResize]="true"` grows it with the text, from `rows` up to `maxRows`, then it scrolls.

</DeviceVariation>

<DeviceVariation title="Floating label" of={InputStories.ModFloating}>

`[floatingLabel]="true"` puts the label inside the field, moving up as people type. It saves height in short forms, like sign-in. Don't use it with a prefix, suffix or icon.

</DeviceVariation>

<DeviceVariation title="Phone keyboard" of={InputStories.ModKeyboard}>

On phones, pick the keyboard and the Return key:

- `inputMode`, like `numeric` for codes. Use it instead of `type="number"`, which adds spinners and drops leading zeros.
- `enterKeyHint`, like `next` between fields and `send` or `done` on the last.
- `autocomplete`, like `one-time-code`, so the phone offers the code from a text message.
- Capitals, autocorrect and spell check are **off automatically** for emails, URLs, passwords, phone numbers, usernames and codes, so "Alex@Example.com" doesn't happen. Set `autocapitalize="words"` on names.

</DeviceVariation>

## Specs

Use **Small / Medium / Large**, **Help / Error** and **Mobile / Web** to see each case. Blue shows the padding inside the field. The numbers are measured from the code.

<SpecPictures of={InputStories.SpecDrawing} />

- **Label to field:** 8px on every device.
- **Field to help or error text:** 4px on the web, 8px on phones, so the message reads as its own line under a taller field.
- **Help text** is grey and **error text** is red, both 14px. An error shows right under the field (above any help text), and the field gets a red border.
- Phone text is 16px or more, so the phone doesn't zoom in when someone taps the field.

## Content

- **Labels** are short nouns in sentence case, with no colon: "Email", "Phone number".
- **Placeholders** show an example of the format, like "name@example.com". They disappear as people type, so never put instructions or the label in them.
- **Help text** says what people need before they type. **Messages** say what went wrong and how to fix it.
- **Make the field as wide as the answer:** a ZIP code field is short, an address field is long.

  <Guideline type="dont" of={InputStories.DontPlaceholderLabel}>use the placeholder as the label. It disappears as people type.</Guideline>
  <Guideline type="do" of={InputStories.DoSpecificError}>say what's wrong and how to fix it.</Guideline>

</DoDont>

## States

<DeviceVariation title="All states" of={InputStories.AllStates} noCode>

Every state, single line and text area. Set them with `state` and `feedback`, `disabled` and `readonly`.

- **Invalid** (red): has to be fixed before the form is sent.
- **Warning** (orange): allowed, but probably a mistake, like a typo in the email domain. People can still send.
- **Valid** (green): only when confirming helps, like a username that's free. Don't mark every correct field.
- **Disabled:** can't be changed yet, and is skipped by <kbd>Tab</kbd>. Explain nearby why.
- **Read only:** a value people can see, select and copy, but not change.

Focus is a blue ring around the field; tab into any field above to see it.

</DeviceVariation>

## Behavior

### Keyboard

| Key | Single line | Text area |
|---|---|---|
| <kbd>Tab</kbd> / <kbd>Shift</kbd> <kbd>Tab</kbd> | Next or previous field, then the clear and show password buttons | Same |
| <kbd>Enter</kbd> | Sends the form | New line |
| <kbd>Esc</kbd> | Empties a `type="search"` field (browser default) | Not used |

### When to validate

- **Check when people leave the field,** not while they type, so they aren't told off halfway through. Emails and most fields work this way.
- **Except new usernames and passwords:** check while people type, so they know the rules are met before they move on.
- **Clear the message as soon as it's fixed,** while they type.
- **On send, check every field,** then move the focus to the first one with a problem.

The reactive forms example in Code does the first two.

### Mobile and web

See [Mobile and web](?path=/docs/foundations-mobile-and-web--docs) for the rules every component follows.

| | Mobile (below 672px) | Web (672px and up) |
|---|---|---|
| Space to help or error text | 8px | 4px |
| Label to field | 8px | 8px |
| Height | 44 / 48 / 48px (small / medium / large) | 32 / 40 / 48px |
| Text | 16px, so the phone doesn't zoom in on focus | 14 to 16px, by size |
| Clear and show password | 44px tap areas | 28px buttons |
| Keyboard | Picked by `type` and `inputMode`, with `enterKeyHint` on the Return key | A physical keyboard |
| Capitals and autocorrect | Off for emails, codes and usernames | Not used |
| Layout | One column, full width | On the grid, sized to the answer |
| Hover | None | On buttons inside the field |

### Edge cases

<SpecimenGrid>
  <Specimen of={InputStories.EdgeLongValue}>**Long value:** scrolls inside the field. Use a text area if long answers are common.</Specimen>
  <Specimen of={InputStories.EdgeLongLabel}>**Long label:** wraps onto more lines. Shorten it, or move the detail into help text.</Specimen>
  <Specimen of={InputStories.EdgeLongError}>**Long message:** wraps under the field. Keep it to one sentence.</Specimen>
</SpecimenGrid>

## Accessibility

For the invalid email in the playground, a screen reader reads:

<ScreenReader name="Email" role="edit text" state="required, invalid entry" description="Enter an email address like name@example.com." />

- **Labels:** every field has a `<label>` tied to it, even with `hideLabel`. A field with no label falls back to its placeholder as the name, but always give it a label.
- **Messages and help text** are linked to the field with `aria-describedby`, so they're read when people reach it.
- **Colour is never the only signal:** invalid, warning and valid fields also show an icon and a message.
- **Contrast:** message text passes 4.5:1. The valid text is a darker green than the valid border to get there.
- **Autocomplete:** set `autocomplete` on personal details, so people with motor or memory difficulties type less.
- **Checked automatically:** every input story runs an accessibility scan in the tests, and a test checks the text above.
